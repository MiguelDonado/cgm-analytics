# CGM Analytics: from sensor readings to a daily glucose dashboard


[![CI](https://github.com/MiguelDonado/cgm-analytics/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/MiguelDonado/cgm-analytics/actions/workflows/ci.yml)

A personal project to learn Airflow while building something useful at the same
time.

I have had type 1 diabetes since I was 12. For most of my life I checked my
glucose with finger pricks. Around five years ago, Spain's public health system
started covering CGM (continuous glucose monitoring) sensors. The sensor is
worn on the arm.

All the data generated by the sensor made it a good fit for an Airflow project. 
The useful part is the dashboard built on top of it: I check it for a few minutes every 
night or a few days per week to see how I can improve my glucose levels.

**Live dashboard:** <https://01a1877e-e313-43cc-1175-1692af9db78a.share.connect.posit.cloud/>
(the first visit after a while takes a few seconds, while the app and the
database wake up)

## Background

I have type 1 diabetes and I use a **FreeStyle Libre 2** sensor for continuous
glucose monitoring (CGM). The sensor is a small device worn on the back of the
arm that measures glucose every few minutes. It sends the readings by Bluetooth
to the **FreeStyle LibreLink** app on my phone. Each sensor lasts 14 days and is
then replaced with a new one.

<p align="center">
  <img src="assets/sensor_arm.webp" alt="Example of a FreeStyle Libre 2 sensor worn on the back of the upper arm" width="500">
</p>

The LibreLink app uploads the readings to Abbott's cloud. Abbott offers
[several apps](https://www.freestyle.abbott/es-es/productos/conectividad.html)
that connect to it, but no public API for getting the readings yourself.

The workaround is **LibreLinkUp**, an app that lets family members or
caregivers follow your glucose readings remotely. It gets the data from
Abbott's cloud through a private API. That API has been reverse-engineered, and
the [`pylibrelinkup`](https://github.com/robberwick/pylibrelinkup) library uses
it to log in as a LibreLinkUp follower and download the readings, which is how
this project gets them.

---

## Objectives

1. **Practice Airflow**: build a real data pipeline that runs every hour,
   instead of following toy examples.
2. **Improve my glucose management**: have a dashboard I can check in a couple
   of minutes each day. If I want to use it regularly, it has to be 
   something simple, that can be interpreted quickly and easily shows which 
   aspects should be improved.
3. **Practice with databases**: design a PostgreSQL database to store the
   readings, load data into it from the pipeline and query it from R for the
   dashboard.

## Workflow

The project has three parts:

1. **Data engineering**: an Airflow DAG runs every hour, extracts the latest
   readings from LibreLinkUp using the `pylibrelinkup` library, transforms them
   and loads them into a PostgreSQL database.
2. **Data analysis**: the readings are analyzed in R with the `iglu` package
   (the AGP report, which includes the summary metrics).
3. **Web application**: a Shiny app turns the analysis into an interactive,
   data-driven dashboard.

## Data analysis

There are many ways to analyze CGM data. The dashboard shows a single view: the
**AGP report** (Ambulatory Glucose Profile), the standard one-page summary of
CGM data, made with `iglu::agp()` for the selected dates. It has three parts.

**1. Summary metrics**, the most common ones:

- **Time in ranges**: percentage of readings in each glucose range. The main
  one is **time in range (TIR)**, between 70 and 180 mg/dL; the others show
  how much time is spent low (below 70 and below 54) and high (above 180 and
  above 250).
- **Average glucose**.
- **Glucose variability (CV)**: coefficient of variation, how much glucose
  swings around its average.
- **GMI** (Glucose Management Indicator): an estimate of HbA1c computed from
  the average glucose.

**2. The AGP.** Summary metrics are useful, but they compress weeks of data
into a single number and lose a lot of information. The AGP stacks all the
selected days onto a single 24-hour day and shows, for each time of day:

- the **median** (50th percentile),
- the **25th–75th percentiles** (the darker band, where half the readings fall),
- the **5th–95th percentiles** (the outer band).

This shows the profile of a typical day: when glucose tends to run high or low,
and how consistent each time of day is.

**3. Daily profiles**: the glucose of each individual day in the selected
range, to spot specific days that went wrong.

This report is enough for a quick, useful review of my glucose. I left out
other metrics on purpose, because most of them are redundant and add little new
information. This is how it looks in the dashboard:

## Deployment

The dashboard is online, so it can be opened from any browser, even when my
laptop is off. Only Airflow stays on the laptop. The database and the dashboard
run in the cloud:

```
Laptop (Airflow, hourly)  ──writes──▶  Neon (PostgreSQL)  ◀──reads──  Posit Connect Cloud (Shiny)  ◀──  browser
```

- **[Neon](https://neon.tech)** hosts the PostgreSQL database. It's managed
  Postgres 17, the same version as the local container, so Airflow and the
  dashboard only needed new connection settings. It has a free plan and scales
  to zero: it pauses when nothing is connected.
- **[Posit Connect Cloud](https://connect.posit.cloud)** hosts the Shiny app. It
  builds the app straight from this GitHub repo, using `dashboard/manifest.json`
  to install the exact R and package versions. The database credentials are set
  as secrets in Connect Cloud, never in the repo.

Details in [`docs/deployment.md`](docs/deployment.md).

### CI/CD

Every step from a code change to the running dashboard is automated:

| Stage | What happens | How |
|---|---|---|
| **Continuous Integration** | Every push and PR runs the unit tests, the SQL tests against a throwaway Postgres, and the DAG checks | GitHub Actions, [`ci.yml`](.github/workflows/ci.yml) |
| **Continuous Delivery** | Pushing a version tag (`v0.2.0`) builds the dashboard image and publishes it to [Docker Hub](https://hub.docker.com/r/migueldonado/cgm-dashboard) | GitHub Actions, [`publish.yml`](.github/workflows/publish.yml) |
| **Continuous Deployment** | Merging into `main` republishes the live dashboard, with no manual step | Posit Connect Cloud, watching the repo |

A separate daily workflow, [`api-check.yml`](.github/workflows/api-check.yml),
logs in to the real LibreLinkUp API, so I find out within a day if Abbott
changes it.

Details in [`docs/ci-cd.md`](docs/ci-cd.md).

## Getting Started

The project can run in two ways. The code is the same in both. Only the
connection settings in the env files change:

| | Cloud (the live setup) | Local |
|---|---|---|
| Airflow | Laptop | Laptop |
| Database | Neon | `cgm-db` container on the laptop |
| Dashboard | Posit Connect Cloud: a web page, from any browser | <http://localhost:3838>|

The local setup needs no accounts besides LibreLinkUp, so it's the quickest
way to try the project.

> [!TIP]
> Instead of following the steps below, you can follow the
> **[local setup video](https://youtu.be/_EkytPnGkLo)**, which goes through
> the whole process.

### Prerequisites

- **[Docker](https://docs.docker.com/get-docker/)**: Airflow, the local
  database and the local dashboard run in containers. On Linux, remember to
  add your user to the `docker` group after installing it.

  Then log out and back in (or restart) for the change to take effect.
- **[Astro CLI](https://www.astronomer.io/docs/astro/cli/install-cli)**: runs
  Airflow locally. No Astronomer account is needed.
- **Freestyle Libre 2 sensor**
- **Freestyle LibreLink app and account**
- **LibreLinkUp follower account.**: in the FreeStyle LibreLink app, go to
  **Connected Apps → LibreLinkUp** and invite an email address. Create a
  LibreLinkUp account with that email and accept the invitation. The project
  logs in with this account to read the readings. To make it crystal clear, the mail and password you used in LibreLinkUp will be the ones you must use in `.env` file.
- **Cloud setup only:** a [Neon](https://neon.tech) account and a
  [Posit Connect Cloud](https://connect.posit.cloud) account (sign in with
  GitHub). Both have free plans. Connect Cloud deploys from a GitHub repo, so
  fork this one.

### Setup

1. **Clone the repository** (or your fork):

   ```bash
   git clone https://github.com/MiguelDonado/cgm-analytics.git
   cd cgm-analytics
   ```

2. **Create the env files.** They hold the credentials and are kept out of
   git. Copy the templates:

   ```bash
   cp cgm-db.env.example cgm-db.env
   cp .env.example .env
   cp dashboard/.env.example dashboard/.env
   ```

   You need all three in both setups. `astro dev start` always starts the
   `cgm-db` and `dashboard` containers, and it fails if `cgm-db.env` or
   `dashboard/.env` is missing, because `docker-compose.override.yml` reads
   them with `env_file`.

3. **Point them at a database**, following **one** of the two options below.

4. **Start everything:**

   ```bash
   astro dev start
   ```

   The first start pulls the dashboard image from
   [Docker Hub](https://hub.docker.com/r/migueldonado/cgm-dashboard).

5. **Load the first readings.** Open the Airflow UI at
   <http://localhost:8080>, switch on the `fetch_glucose` DAG and click
   **Trigger**. The first run creates the table. From then on, the DAG runs
   every hour on its own. LibreLinkUp only returns about the **last 12 hours**
   of readings, so the history starts the day you set this up. Keep Airflow
   running.

6. **Open the dashboard** at <http://localhost:3838> (or your Connect Cloud
   URL).

   > [!WARNING]
   > The AGP report only works once there are **more than 24 hours** of
   > readings in the database. Until then the dashboard can't build it, so
   > leave the DAG running for at least a day before checking it.

> `astro dev stop` stops the containers and keeps the readings. In the local
> setup, avoid `astro dev kill`: it can delete the database volume, readings
> included.

To update the pipeline or the dashboard after changing the code, see
[`docs/deployment.md`](docs/deployment.md#making-changes).

#### Option A: local database

| File | Used by | What to set |
|---|---|---|
| `cgm-db.env` | The `cgm-db` container | `POSTGRES_PASSWORD`: choose a password |
| `.env` | Airflow | The same password in `AIRFLOW_CONN_CGM_DB` (host `cgm-db`, as in the template), and your LibreLinkUp email and password in `AIRFLOW_CONN_LIBRELINKUP` |
| `dashboard/.env` | The dashboard container | The same password in `CGM_DB_PASSWORD` (host `cgm-db`, as in the template) |
| `dashboard/.Renviron` | R, when running the app from RStudio (optional) | The values below |

`dashboard/.Renviron` has no template. Create it only if you want to run the
app from RStudio instead of Docker. R runs on the host, so it connects through
the port published on the host instead of the Docker network:

```bash
CGM_DB_HOST=localhost
CGM_DB_PORT=5433
CGM_DB_NAME=cgm
CGM_DB_USER=cgm
CGM_DB_PASSWORD=<the same password>
```

#### Option B: cloud database (Neon) and dashboard (Connect Cloud)

1. **Create a Neon project** with Postgres 17. Copy the connection string from
   the **Connect** button. It contains the host, user and password used below.

2. **Fill in the env files** with the Neon values:

   | File | Used by | What to set |
   |---|---|---|
   | `.env` | Airflow | `AIRFLOW_CONN_CGM_DB='postgresql://<neon-user>:<neon-password>@<neon-host>:5432/<db>?sslmode=require'`, and your LibreLinkUp account in `AIRFLOW_CONN_LIBRELINKUP` |
   | `dashboard/.env` | The local dashboard container | `CGM_DB_HOST`, `CGM_DB_USER`, `CGM_DB_PASSWORD` and `CGM_DB_NAME` from Neon, port `5432` |
   | `dashboard/.Renviron` | RStudio (optional) | The same values as `dashboard/.env` |
   | `cgm-db.env` | The `cgm-db` container | Any password. The container still starts, but nothing uses it |

3. **Publish the dashboard** on Connect Cloud: **Publish → Shiny**, your fork,
   branch `main`, primary file `dashboard/app.R`. Under **Variables**, add the
   five `CGM_DB_*` values from `dashboard/.env`. The first build takes a few
   minutes.

Details, and how to copy readings from a local database into Neon, are in
[`docs/deployment.md`](docs/deployment.md).

To switch from one setup to the other later, change the env files, then run
`astro dev restart`. For `.Renviron`, also restart the R session. The readings
stay in the old database. They are not moved.
